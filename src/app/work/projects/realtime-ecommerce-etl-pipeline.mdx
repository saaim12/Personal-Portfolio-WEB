## The problem

Order events arrive continuously, while reporting needs consistent customer, product, date, and sales records. I built a pipeline that separates event capture from validation and reporting so changes to the analytical model can be applied to retained source data.

## What I built

A producer publishes order events to Kafka. PySpark Structured Streaming consumes the events and writes checkpointed Parquet data, partitioned by date, to storage compatible with S3.

The bronze layer retains source events. A batch transformation validates and deduplicates those records into silver. The next transformation builds gold as a PostgreSQL star schema with customer, product, and date dimensions around a sales fact table.

Airflow orchestrates the hourly batch stages. The producer and streaming consumer run separately from those scheduled tasks. Docker Compose provides the container setup, with storage and database connections configured for the chosen environment.

## Engineering decisions

**Preserve source events.** Retaining bronze data makes it possible to rebuild downstream tables when validation rules or reporting definitions change. The additional storage buys a repeatable source for those transformations.

**Separate streaming from batch orchestration.** Kafka and Spark handle continuous ingestion. Airflow manages tasks with a defined start and completion. Reporting freshness therefore depends on the batch schedule as well as processing time.

**Model data for reporting.** A central sales fact table and shared dimensions provide a consistent structure for analytical queries. Changes to dimension keys and business definitions still need to be coordinated across the pipeline.

## Result and next steps

The implementation connects order ingestion, validation, deduplication, and scheduled transformations to a warehouse with four tables. The repository and article document the pipeline and its container setup.

My next priorities would be data quality checks between layers, recovery tests for interrupted jobs, and benchmarks with documented event volumes and hardware. A managed AWS deployment would require its own capacity, access, cost, and recovery design.

## Technical architecture: component responsibilities

| Component | Responsibility | Operational consideration |
| --- | --- | --- |
| Event producer | Emit order events into Kafka | Event schema and replay inputs |
| Kafka | Decouple producers and consumers | Retention, partitions and consumer offsets |
| Spark Structured Streaming | Read events and write partitioned Parquet | Checkpoint location and restart behavior |
| Bronze object storage | Preserve ingested raw data | Reprocessing and source traceability |
| Airflow | Orchestrate hourly batch transformations | Dependency failures and scheduled freshness |
| Silver transformation | Validate, standardize and deduplicate | Deterministic handling of duplicate records |
| PostgreSQL gold | Persist sales facts and dimensions | Relational keys and analytical consistency |

## Warehouse model and consistency

The gold layer centers on a sales fact table with customer, product and date dimensions, giving the implementation **four warehouse tables**. A star schema separates descriptive attributes from the measures needed by reports. The bronze/silver/gold stages are logical responsibilities of this pipeline; they are not evidence of a separately managed lakehouse product.

**Failure boundary:** continuous Kafka/Spark ingestion and hourly Airflow runs do not share the same schedule. A successful event ingest does not mean it has already appeared in the reporting tables. Checkpoints help Spark recover processing progress; warehouse load semantics, business-level deduplication, and backfill correctness are independent concerns that should be tested explicitly.

**Environment boundary:** the published example uses local containerized computation, S3-compatible object storage, and a configured PostgreSQL target. It should not be presented as a production-managed AWS Kafka or EMR deployment.

## Evidence and next experiments

The source repository documents runnable pipeline components and the linked Medium article walks through the architectural trade-offs. End-to-end throughput, recovery time, and warehouse freshness are not published as measured service-level targets. The next useful benchmark would record event rate, batch sizes, job duration and reproducible hardware/configuration alongside data-quality checks.
