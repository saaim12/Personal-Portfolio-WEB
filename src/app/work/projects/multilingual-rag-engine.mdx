## The problem

A document Q&A service needs to retrieve relevant material without mixing customer datasets. I built this project for multilingual questions over separate knowledge bases, with authentication, usage quotas, and answers based on retrieved context.

## What I built

Django exposes ingestion and query workflows over PostgreSQL with pgvector. Documents are divided into chunks and embedded locally using a multilingual E5 model. The service stores each chunk with its customer association and uses that association when searching for context.

At query time, the service embeds the question, retrieves relevant chunks for the authenticated customer, and sends the selected context to Gemini for answer generation. A browser interface supports the query workflow.

Six prompt templates cover question answering, summarization, translation, glossary creation, extraction, and explanation. Usage quotas provide a limit on requests per customer.

## Engineering decisions

**Carry identity through retrieval.** The verified token supplies the customer identity used by the query layer. This boundary also depends on registration, token issuance, and authorization checks across ingestion and retrieval. Assigning a customer from an email domain alone does not prove membership of that organization.

**Keep embeddings local.** Local embedding avoids a separate embedding API and its request charges. It still requires memory and compute within the deployment. Gemini receives retrieved context for generation, so the service has a separate external data processing boundary.

**Store vectors with their source records.** PostgreSQL and pgvector keep document metadata and embeddings together. This simplifies the data model and operations, while retrieval performance still depends on indexing and the size of each dataset.

**Use context to guide generation.** Retrieved passages give the model relevant material to work from. They do not guarantee that every generated statement is supported, so answer quality needs evaluation alongside retrieval quality.

## Result and next steps

The project brings authentication, multilingual retrieval, ingestion, quotas, and prompt templates into one service. The accompanying article explains the implementation and setup decisions.

My next priorities would be a representative multilingual evaluation set, authorization tests for every data access path, and concurrent quota tests. Retrieval precision, response latency, and operating cost should be measured against a documented workload before setting service targets.

## Architecture: ingestion versus authenticated retrieval

| Stage | Component | Engineering responsibility |
| --- | --- | --- |
| Ingestion | Django administrative endpoints | Accept and associate supported source documents with a customer |
| Preparation | Text extraction and chunking | Produce searchable source passages |
| Embedding | Local multilingual E5 model | Encode passages without calling an external embedding API |
| Storage | PostgreSQL + pgvector | Store vectors together with tenant-linked source records |
| Authentication | JWT verification | Establish caller identity from validated claims |
| Retrieval | Tenant-scoped similarity query | Restrict candidate chunks before answer generation |
| Generation | Gemini + prompt template | Generate a response using selected context |

## Security and correctness boundaries

**Tenant identity is not a search parameter.** Retrieval must use the authenticated customer's identity rather than trusting a client-supplied tenant ID. This must be enforced consistently in ingestion permissions, chunk ownership, vector search and any subsequent source-document access. A vector rank alone is not an authorization check.

**Embedding and generation have different external dependencies.** The multilingual embedding model runs locally, whereas selected retrieval context is sent to Gemini for generation. This makes the model-provider boundary relevant to what source material can leave the service.

**Quotas are separate from isolation.** Per-customer request limits constrain usage; they do not replace tenant-aware database filtering. Concurrent requests and quota enforcement should be tested independently.

## Validation and limitations

Six prompt templates support distinct tasks, but the existence of multiple prompts does not itself measure answer quality. Useful follow-up evaluation includes cross-tenant negative tests, multilingual retrieval precision, unsupported-answer behavior, concurrency under quotas and observed request latency. Do not claim benchmark scores or production-scale reliability without a published evaluation methodology.
