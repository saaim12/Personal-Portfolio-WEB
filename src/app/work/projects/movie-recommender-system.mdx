## The problem

A recommendation model needs a serving workflow that applications can use. I built this project to combine MovieLens data preparation, model training, evaluation, and API serving, with a fallback signal for users who have little interaction history.

## What I built

The pipeline combines ratings, tags, links, and movie metadata into an item catalogue. Scoring blends content similarity, item cooccurrence, and popularity. These signals cover different cases, from movies with shared attributes to items that appear together in user histories.

Training and evaluation run separately from request handling. The trained model is saved as an artifact that the FastAPI application loads. The API exposes recommendation, similar item, health, and model reload endpoints with API key protection.

The project includes optional Redis caching, Docker configuration, structured logging, request tracing, and testing workflows. Airflow coordinates the training pipeline.

## Engineering decisions

**Separate training from serving.** A saved artifact gives the API a defined model version to load. It also creates an explicit place to validate a candidate model before replacing the current one.

**Combine complementary signals.** Content and popularity help when interaction history is sparse. Item cooccurrence adds a behavioral signal. Their relative value needs to be tested against simple baselines rather than assumed from the model design.

**Make model reload an explicit operation.** Reloading supports a model release schedule separate from application releases. Safe rollout still requires artifact validation, cache invalidation, and concurrent request testing.

## Result and next steps

The project provides a modular path from MovieLens data to recommendation APIs. It demonstrates the serving and operational concerns around a model as well as the scoring logic.

My next steps would be evaluation with a chronological split, comparisons that remove each scoring signal in turn, and load tests for cold requests, cached requests, and model reloads. Evaluation reports should include the number of eligible users so quality metrics can be interpreted in context.

## Training and serving interfaces

| Layer | Technology / data | Responsibility |
| --- | --- | --- |
| Source | MovieLens ratings, tags and metadata | Build catalogue and interaction signals |
| Model preparation | Python and data processing | Construct item features and co-occurrence signals |
| Ranking signals | Content similarity, co-occurrence, popularity | Combine complementary recommendation evidence |
| Artifact | Serialized trained model | Separate model preparation from API deployment |
| API | FastAPI | Serve recommendations and related-item responses |
| Operations | Health, reload, optional Redis | Support process observability and cache-backed responses |

A model reload endpoint is an implementation capability, not proof of zero-downtime model replacement. Safe reload must validate candidate artifacts and account for concurrent requests, cache invalidation and rollback.

## Evaluation considerations

Popularity-based results provide an understandable fallback for sparse interactions. Strong evidence of ranking quality would require a reproducible train/evaluation split, appropriate ranking metrics and a baseline comparison. The current portfolio does not assert an unverified improvement in precision, recall or click-through rate.
